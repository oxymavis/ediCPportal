# Database Deploy Notes - 2026-03-25

## Scope

This deployment note covers database-affecting changes introduced on 2026-03-25.

## Schema Changes

### Migration `0003_api_client_owner.py`

Purpose:
- Add ownership metadata to self-service OAuth client records.

Change:
- Add owner/user linkage fields to `api_clients` so generated developer apps can be scoped to the creating user.

### Migration `0004_as2_sender_receiver_fields.py`

Purpose:
- Persist partner AS2 routing identifiers required for external partner setup.

Change:
- Add the following columns to `as2_profiles`:
  - `as2_port`
  - `sender_id`
  - `sender_qualifier`
  - `receiver_id`
  - `receiver_qualifier`

Impact:
- Partner create and AS2 profile edit APIs now require/return these fields.

### Migration `0005_certificate_raw_content.py`

Purpose:
- Persist uploaded or pasted PEM/Base64 certificate text.

Change:
- Add `raw_content` to `certificates`.

Impact:
- Certificate create/read/update APIs now support `rawContent`.

## Deployment Steps

Run database migrations before deploying the updated application code:

```bash
cd backend
alembic upgrade head
```

## Post-Deploy Checks

Verify the following after migration:

1. A developer user can create a developer app and receive `client_id` and `client_secret`.
2. Partner creation accepts `as2Port`, `senderId`, `senderQualifier`, `receiverId`, and `receiverQualifier`.
3. Existing partner detail and partner list APIs return the five AS2 routing fields.
4. Certificate upload accepts either file input or pasted PEM/Base64 `rawContent`.
5. Certificate records can be retrieved with `rawContent`.

## Runtime Compatibility

The app startup includes compatibility column-add logic for these new fields, but that logic is a fallback only.

Required deployment approach:

1. Run Alembic migrations.
2. Deploy backend.
3. Deploy frontend.

Do not rely on runtime fallback in place of formal migration execution for production environments.

## TencentDB / MySQL production notes (operational)

### VPC vs public endpoint

- Prefer **same VPC + private IP** for CVM → TencentDB when possible.
- If CVM and DB are in **different VPCs** without peering, private IP connectivity may **time out**; you may temporarily use the **database public endpoint** (non-default port) and tighten security group rules. Plan to converge on VPC-internal access for production.

### `sessions.id` length (JWT session id)

If login or session insert fails with MySQL error **1406 / Data too long for column `id`** on table `sessions`, the stored session id (JWT string) exceeds the column width. Apply **once** on the target database (replace host/user as appropriate):

```sql
ALTER TABLE sessions MODIFY COLUMN id VARCHAR(512) NOT NULL;
```

Re-run application health and `POST /v1/auth/login` smoke tests after the change.

### Run migrations on the server (CVM)

When deploying with [`scripts/deploy-cvm.sh`](../scripts/deploy-cvm.sh), migrations run automatically via:

`PYTHONPATH=backend alembic -c backend/alembic.ini upgrade head`

Ensure `backend/.env` on the server points at the correct `DATABASE_URL` before deploy.
